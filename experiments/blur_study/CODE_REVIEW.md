# Trace the Linux blur-study pipeline

Open `foundation-model-analysis` as the editor workspace and choose the numbered **Blur** entries in Run and Debug. Select the Linux training environment in VS Code when connected to Linux. On Windows the launches use the workspace's VGGT interpreter. Set a breakpoint on an executable statement in the gutter, start with F5, use F10 to execute that statement, and F11 to enter the function it calls. A stopped line has yet to execute.

The production commands are in [README.md](README.md). The debugger walks the same Python entry points with smaller inputs. Steps 01–03 write one example from each source under `outputs/blur_review/unified`. From step 04 onward the launches read the complete prepared `data/unified` tree. Steps 05–07 then create the review splits, schedule, and evaluation cohort under `outputs/blur_review`. The Linux run uses the full schedule in this directory alongside this guide (`experiments/blur_study/schedule.json`).

## Data preparation

1. **Fetch one uCO3D recording.** On a fresh Linux data directory the first command from the repo root is `python experiments/blur_study/dataset_prep/fetch_uco3d.py fetch`. For the walkthrough choose **Blur 01 | Fetch one uCO3D recording** and press F5. This launch automatically pauses as the file opens, before any transfer. In the same file, use **Run to Cursor** at `fetch(args)`. Inspect `args.manifest`, `args.scenes` and `args.dest`, then press F11 to follow the call. In `fetch`, stop at `total = sum(...)`. Inspect `ids[0]` and `index["members"][ids[0]]`. Compare the ID with the v2 manifest and the member name, shard, offset and size with `dataset_prep/uco3d_shard_index.json`. In `fetch_one`, step into `download_and_extract(entry, staging, session)`. Break at `with session.get(...)` to see the byte interval, then return to `fetch_one` with the extracted scene path. Continue to `validation = validate_scene(scene)`, step over, and inspect `validation["errors"]` and `validation["frames"]`. On a repeat run, inspect the early return for an existing scene with a completion record. The repository's `.gitignore` allows the manifest and index to travel with the code.
2. **Convert one Hypersim recording.** Start at `convert_hypersim.py:main` in `dataset_prep/`. Follow `run` into `convert_common.py`, then `_convert_one → build` back in the converter. At `depth = h.planar_depth(...)`, compare one valid pixel in `range_map` with the resulting depth. Step into `hypersim_io.py` to see how the camera ray determines this value. Inspect `pose.shape`, the frame ID, and `camera.warp`. Follow `write_scene` in `unified_io.py` through the staged EXR readback and completion record. Both converter launches set one worker so these breaks happen in the current process.
3. **Convert one MVS-Synth recording.** Follow `convert_mvssynth.py:main → convert_common.run → build`. Stop at `pose = json.loads(...)` and compare the matching image, EXR, and pose filenames. Step into `cam_from_world` to inspect the world-axis reflection. In `unified_io.clean_depth`, compare a nonfinite input pixel with its output. [MAPPING.md](dataset_prep/MAPPING.md) documents the source conventions used by both converters.
4. **Validate a dataset.** In `dataset_prep/validate_unified.py:main`, stop at `report = {...}` to inspect `expected` and `present`. Follow `geometry_check → geometry.reproject_score`, then return to `doc = ...` and compare the documented inlier fraction with the control scores. Continue into `loader_probe` to inspect a real ten-view training sample. The saved uCO3D reports fail the two-times-best-control threshold. The validator returns a nonzero exit code for that result.
5. **Generate the split lists.** Start at `prepare_splits.py:main`, at `splits = load_splits(args.manifest)`. `_paths.py` supplies the v2 manifest. Follow `load_splits → data.blur_schedule.manifest_recordings` to watch the filter turn one CSV row into a dataset key and sequence name. Back in `check_splits`, inspect `counts` and `overlap`. At `write_text`, inspect `key`, `split`, and `names`. The full run produces the six files in `splits/`, totalling 450 train and 50 held-out recordings.
6. **Build the shared schedule.** Start at `build_schedule.py:main` at `cfg = load_config(...)`. Inspect the dataset entries resolved from `training/config/blur_study.yaml`. Follow `schedule = build_schedule(...)` into `training/data/blur_schedule.py`. At `samples.append(...)` inspect one recording's frame IDs, augmentation seed, blur permutation, and four recipe counts. The frame-sampling callback enters `training/data/datasets/unified.py:sample_frame_ids`. Return to the builder's `output.write_text(...)` and inspect `schedule["schedule"][0]["batches"][0]`. The debug launch writes one pass of six single-recording batches. The Linux schedule contains five passes of 150 three-recording batches.
7. **Prepare source validation.** Start at `eval/prepare_source_val.py:main` at `check_benchmark_frames(rows)`. Follow one iteration through `draw_distinct` and `export_scene`. Inspect `rec`, the ten source indices in `ids`, and the frame order in `names`. Compare the selected source indices with the exported frame map's positions 0–9. Production evaluation consumes `eval/frames/source_val.json` and the corresponding `data/source_val` scene folders.

## Training and evaluation

8. **Train one recipe.** The Linux driver is `run_linux.sh`. Start at the call to `run_recipe` and follow its `torchrun` command into `training/launch.py:main`. The numbered Python launch enters this same file directly with one GPU, two steps, and zero loader workers for stepping. Choose `fixed` to see two blurred views in each sample.
   - Break at `Trainer(**load_config(...)).run()` and step into `load_config`. Inspect the resolved recipe, schedule path, model weights, loss, and optimizer before the config-only keys are popped.
   - In `training/trainer.py:_setup_components`, follow the initial weight load and `apply_lora` into `training/train_utils/lora.py`. Inspect one matched linear layer and the trainable adapter parameters.
   - Follow `run_train → get_loader → ScheduledBlurDataset.__getitem__` in `training/data/scheduled_dataset.py`. Inspect `sample["frame_ids"]` and the selected blur positions. Follow `get_data → _load_views` in `unified.py` to the call into `vggt_omega/utils/synthetic_blur.py`. Inspect source width and kernel width. Return to `training/data/composed_dataset.py:postprocess` and then to `return out` in the scheduled dataset to see the final `blur_mask`.
   - Back in `trainer.py:train_epoch`, stop at `self.scaler.step(optim.optimizer)`. Follow the end of the pass through `save_checkpoint` and `_save_lora_outputs`. Review checkpoints are under `training/logs/review_<recipe>/checkpoints`. Repeating a recipe resumes its latest checkpoint; a completed run can skip the training iterations.
9. **Export weights.** Choose the same recipe. Break in `export_merged.py:export` at `merged = merge_lora_state_dict(...)`. Step into the merge, inspect the scale `alpha / r`, then return to the strict load into plain `VGGTOmega`. The exported file is the input to 10b.
10. **Evaluate original and trained weights.** Run 10a, then 10b for each exported recipe. In `eval/motion_blur.py:main` follow `run_scene` for `hypersim__ai_001_003_cam_00`. Inspect the ten frame indices, the first selected blur assignment, and the call to the shared blur primitive. Return to `report["meta"]` in `main` and inspect the model, scene and blur settings saved with the metrics. The full Linux driver `eval/run_study_eval.sh` repeats this entry point for each model and cohort before invoking the summary.
11. **Summarize.** In `eval/summarize_study.py:main` break at `check_curves(model, results[model])`, then at `rows = build_rows(results)`. Inspect a row for zero blurred views and one for two blurred views. For a signed difference from clean fine-tuning, run steps 08, 09 and 10b for both `clean` and a blur-trained recipe on the same scene. Markdown and CSV go under `outputs/blur_review/results/summary`.

The two optional shell-wrapper launches use the Bash Debug extension on Linux. The training wrapper starts a full fixed-recipe run in its regular production log and checkpoint directories. The numbered launches use the Python Debugger extension and their own review output locations.
